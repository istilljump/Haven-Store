## 设计决策

1. **常量类 ProductConstant**：收敛交易方式（线上/线下）、合法成色（全新/九成新/八成新/七成新及以下）、
   经纬度范围（-180~180/-90~90）到常量类，系统内禁止魔法值
2. **校验分层**：
   - DTO 层（JSR-303 注解）：格式与范围校验，新增经度 `@DecimalMin(-180)` / `@DecimalMax(180)`、
     纬度 `@DecimalMin(-90)` / `@DecimalMax(90)` 越界校验
   - Service 层（业务校验）：交易方式合法性、成色合法性、分类存在性、线下模式联动校验（跨字段逻辑无法用 JSR-303 表达）
3. **线下联动校验**：交易方式为「线下」时地址/经度/纬度必填，为「线上」时允许为空；
   与 RegisterDTO 的两次密码校验采用同一模式（业务层校验跨字段约束）
4. **BusinessException 双参构造**：新增 `BusinessException(Integer code, String message)` 构造方法，
   参数校验失败统一返回 400（PARAM_ERROR），而非 500（BUSINESS_ERROR），语义更精准
5. **DTO→Entity 转换提取**：将 addProduct 中的手工赋值提取为 `buildProduct(dto, userId)` 私有方法，
   后续商品编辑等接口可复用

## 优化点总结

- 参数校验从 DTO 层单层（JSR-303）增强为 DTO + Service 双层校验
- 线下交易联动校验补全（跨字段约束），杜绝线下商品无地址/经纬度的脏数据
- 分类 ID 存在性校验，防止前端传入不存在的分类导致数据完整性问题
- 常量收敛到 ProductConstant，消除魔法值
- BusinessException 新增双参构造，参数校验异常统一 400
- DTO→Entity 转换提取为独立方法，增强可读性与可复用性
