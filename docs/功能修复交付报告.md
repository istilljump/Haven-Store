## 二、核心根因：管理后台登录后被打回登录页

原代码里 `AdminLayout.vue` 与 `utils/auth.js` 对 localStorage 的 key 理解不一致：

```
utils/auth.js:11       const USER_INFO_KEY = 'user_info'   ← 登录成功时写入这个 key
AdminLayout.vue:181    localStorage.getItem('userInfo')    ← 守卫读的是这个 key（多一个下划线）
```

守卫逻辑是「读不到用户信息就跳回登录页」，因此**登录成功 → 一进后台立刻被弹回登录页**。

**修复**：`AdminLayout.vue` 改为统一使用 `utils/auth` 的 `getUserInfo()`，
并把 `/admin/**` 的权限校验从组件内（每次挂载都重复注册守卫）收敛到 `router/index.js` 的全局守卫，一处生效。

# 第五轮修复：登录报「系统内部错误」

**现象**：用 `testuser1` 与管理员的账号登录，页面提示「系统内部错误」，接口返回 `{"code":501}`。

## 一、根因：Redis 未运行，而登录强依赖缓存写入

后端日志里的真实异常：

```
Caused by: io.lettuce.core.RedisConnectionException: Unable to connect to localhost:6379
Caused by: java.net.ConnectException: Connection refused: getsockopt: localhost/127.0.0.1:6379
```

登录流程里有一行把用户信息写入 Redis 当作缓存：

```java
redisUtil.set(RedisKeyConst.USER_INFO_KEY + user.getId(), user, tokenExpiration, TimeUnit.MILLISECONDS);
```

Redis 一挂，这行直接抛异常 → 被全局异常处理器转成 501。
**缓存不可用导致核心业务不可用，这是设计缺陷，不只是环境问题**——所以这次不只是把 Redis 启起来，而是改了代码。

## 二、修复：区分「缓存」与「存储」两种失败语义

`RedisUtil` 增加了三个安全版本，失败只记警告日志，不打断业务流程：

| 方法 | 用途 | 失败行为 |
|---|---|---|
| `setQuietly` / `getQuietly` / `deleteQuietly` | 纯缓存（登录后缓存用户信息、缓存失效） | 记 WARN，继续执行；`getQuietly` 返回 null 由调用方回源数据库 |
| `set` / `get` / `delete`（保留） | 真正的存储（系统设置以 Redis 为存储） | 正常抛异常 |
| `isAvailable` | 供健康检查探测 | 返回 true/false |

各调用点已按语义分类：

- 用户模块的 6 处（登录写缓存、读缓存、重建缓存、3 处改资料/改密/换头像后的缓存失效）→ 安全版本
- 管理端的用户状态变更缓存失效 → 安全版本
- **系统设置的读取** → `getQuietly`，Redis 不可用时返回默认值，保证设置页还能打开
- **系统设置的保存** → 保持抛异常，但换成明确提示「系统设置存储暂不可用，请确认 Redis 服务已启动」——
  写入失败不能静默成功，否则管理员会以为设置保存了

## 三、连带修复的两个问题

### 1. 健康检查暴露依赖状态（正是缺少它才需要翻日志定位）

`GET /health/detail` 原先 `databaseStatus` / `cacheStatus` 是 TODO 占位，从没实现。
现在真实探测并返回：

```json
{"status":"UP","app":"haven-store-backend","version":"1.0.0",
 "databaseStatus":"UP","cacheStatus":"DOWN"}
```

同时把公开路径从 `/health` 放宽为 `/health/**`：健康检查端点应允许探针免登录访问
（此前 `/health/detail` 会返回 401，监控系统根本拿不到状态）。

### 2. 图片静态映射的潜伏 bug（首次启动/全新克隆时图片全 404）

`WebMvcConfig` 里注册上传目录时：

```java
String location = Paths.get(uploadDir).toAbsolutePath().normalize().toUri().toString();
registry.addResourceHandler("/uploads/**").addResourceLocations(location);
```

问题在于 **`Path.toUri()` 只有在路径已存在时才会补结尾的 `/`**，而 Spring 的资源路径
必须以 `/` 结尾才会被当成目录。于是：

- 启动时 `uploads/` 目录**存在** → 一切正常（之前的测试碰巧都是这种情况）
- 启动时目录**不存在**（全新克隆、清理过目录）→ 映射失效 → **商品图片与头像全部 404**

这个 bug 平时看不出来，我清理上传目录后复现了。修复：启动时用 `Files.createDirectories`
确保目录存在，并且**显式补上结尾的 `/`**，不再依赖 `toUri()` 的隐式行为。
